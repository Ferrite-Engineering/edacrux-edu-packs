# cocotb-driven-testbench — instructor notes

## Learning objectives recap

1. Read a structured cocotb log file (severity, logger name, body,
   simulation-time prefix).
2. Load a cocotb log into WaveCrux as a sibling overlay to the VCD.
3. Click log lines to jump the cursor to the matching simulation
   time.
4. Filter the log by severity and by keyword.

## On the "cocotb runs but is not required" claim

This pack documents the cocotb test in `tb/test_uart_rx.py` but the
checked-in `fixtures/reference.vcd` is generated by the pure-Verilog
`tb/tb_uart_rx.v`, and the checked-in `fixtures/cocotb_run.log` is a
hand-curated log that mirrors what the cocotb test *would have*
produced (the timestamps line up with the real waveform events).
This keeps the EDU pack build pipeline lean — instructors who don't
have cocotb installed can still rebuild fixtures.

If a student or instructor *does* have cocotb 2.0.1 installed, they
can run the Python test directly (instructions at the top of
`tb/test_uart_rx.py`) and the resulting VCD + log should match the
checked-in artifacts byte-for-byte.

## Stimulus and timing summary

- 50 MHz clock, reset until t = 45 ns.
- 100 ns idle window so the receiver IDLE state is visible.
- 4 bytes sent: 0x55, 0xAA, 0x55, 0xAA at 115_207 baud.
- Per-byte cadence:
  - Start bit at t = 145 (byte 1), 83620 (byte 2), 171420 (byte 3),
    259220 (byte 4).
  - `rx_valid` pulses at t = 82620, 170420, 258220, 346020 with the
    full byte on `rx_data`.
- Total simulation length: 352345 ns ≈ 352 µs.

Machine-checkable contract in [`../fixtures/expected.json`](../fixtures/expected.json).

## Exercise answers

**Exercise 1.** Clicking the `78265.00ns ... Driving stop bit` line
jumps the cursor to t = 78265 ns. At that moment `rx = 1` (the stop
bit is being driven high) and the receiver FSM is in `state = 2` (the
DATA state, just finishing the 8th data bit — the receiver
transitions to STOP on the next sample edge a few hundred ns later).

**Exercise 2.** Difference is 83620 − 82620 = 1000 ns. That matches
the `await Timer(1000, units="ns")` in the cocotb test exactly.

**Exercise 3.** A failing test would emit an assertion line like:

```
170420.00ns ERROR    UartRxTest                         Received byte 0xCC (expected 0xAA)
170420.00ns ERROR    cocotb.regression                  uart_rx_receives_four_bytes failed
```

at the byte-completion timestamp where the mismatch was detected
(170420 ns for byte 2). Accept any answer that mentions the
mismatch message + the time of detection.

## Common student mistakes

- **Expecting log lines to land at sub-nanosecond times.** cocotb's
  default log granularity is 1 ns; the log timestamps for the bit
  drives are aligned to the sim-time at which the Python `await
  Timer(...)` call resumed. They do *not* line up with the actual
  posedges of the system clock at sub-ns resolution.
- **Confusing the cocotb log overlay with X-trace.** Both are
  navigation aids but they work differently. The cocotb log uses
  authored log messages with explicit timestamps. X-trace walks
  fan-in cones using the netlist structure. Coach the distinction.

## Re-running the build

```bash
cd packs/cocotb-driven-testbench
./build.sh
```

The pure-Verilog testbench `tb/tb_uart_rx.v` produces
`fixtures/reference.vcd`. The companion log
`fixtures/cocotb_run.log` is checked in and is not regenerated by
`build.sh` (it would require running the cocotb test, which is
optional).
