# Flow fixtures: provenance

Two captured place-and-route runs of `src/path_adder.v` on an iCE40 UP5K, one
constrained to 1000 MHz (a violation) and one to 12 MHz (met). They are real
tool output, copied from the SimCrux open-core nextpnr fixture set
(`verification/fixtures/flow/nextpnr` in <https://github.com/Ferrite-Engineering/simcrux>,
cases `path_ice40_violated` and `path_ice40_met`, repository licence Apache-2.0,
Copyright 2026 Ferrite Engineering LLC). Only what this pack needs was copied.

## Tools and date

Captured on 2026-10-21 with OSS CAD Suite tag `2026-10-21`, darwin-arm64.
`versions.txt` holds the exact version lines the tools printed (Yosys
0.70+186, nextpnr 0.11.1-77). nextpnr and Yosys are ISC-licensed; their output
carries no licence of its own.

## Command

Per case, in a scratch directory with the RTL copied in, so source spans read
`path_adder.v:16.14-16.27` and never an absolute path:

```
yosys -q -p "read_verilog path_adder.v; synth_ice40 -top path_adder -json netlist.json"
nextpnr-ice40 --up5k --package sg48 --json netlist.json --freq <MHz> \
    --report report.json --detailed-timing-report --log pnr.log
```

`<MHz>` is 1000 for `violated-1000mhz` and 12 for `met-12mhz`. The exit status
nextpnr returned is in `exit_code.txt` (1 and 0). Home and scratch paths are
scrubbed from every file.

## What was changed

- The synthesised netlist is named `synth.json` here; the source set names it
  `netlist.json`. SimCrux maps a worst path to the RTL only against a file of
  that name inside the run directory, and lists the path unmapped without it.
- The violated case has no netlist of its own in the source set because it
  shares the met case's synthesis; the same file is stored in both run
  directories here, so each directory is a complete run on its own.
- The capture's `verdict.expected.json` and `max_frequency.txt` were left out.

## Layout

The runs sit in `runs/path_adder/<run>/`, the shape SimCrux gives its own runs
(`runs/<entry>/<tag>/`), so an ingested run is filed under the design
`path_adder` and its worst path can open `src/path_adder.v`.

## Where each expectation comes from

Nothing in `fixtures/expected.json` was generated by SimCrux. The values were read
from the run's own files, then checked again by `tools/edacrux-pack-verify`
on every push, which recomputes each one from those files.

| Expectation | Read from |
|---|---|
| Verdict `violated` (1000 MHz) and `met` (12 MHz) | `jq '.fmax'` on `report.json`: `achieved` against `constraint` for every clock. The last `Max frequency for clock` line of `pnr.log` says FAIL and PASS respectively, which agrees |
| Achieved frequency, 60.9 MHz | `jq '.fmax[].achieved'` on `report.json` (the same placement result in both runs) |
| Worst path starts at a cell named for `src_a`, ends at `sum_q` | `jq '.critical_paths[0].path'` on `report.json`: the first segment's `from.cell` (`src_a_SB_DFF_Q_23_DFFLC`) and the last segment's `to.cell` (`sum_q_SB_DFF_Q_DFFLC`) |
| The end register is computed on line 16, declarations on lines 10 to 12 | `src/path_adder.v`, by reading it: `sum_q <= src_a + src_b` is the only logic between registers |
| `synth.json` has cells from line 16 | the `src` attributes of `synth.json`: `path_adder.v:16.14-16.27` |

The register named at each end is derived from the RTL and the tool's own cell
names (an iCE40 flip-flop cell is named after the RTL register it implements);
the path's frequency and delays move with every tool build, so no expectation
pins a delay.
